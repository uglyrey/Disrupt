# Вход и привязка Telegram в реальном времени

Статус: код и тесты написаны, серверные тесты и проверка в настоящем браузере против локального сервера пройдены. DOM-тесты jsdom локально не запускались, их проверит CI. Живой Telegram не проверялся. Бот и внутренний API не менялись.

## Что было не так

1. «Войти через Telegram» сначала ждал ответ сервера и только потом показывал ссылку «Открыть Telegram». Браузер разрешает открыть окно только прямо из нажатия, поэтому второе нажатие было обязательным.
2. Страница опрашивала сервер раз в 2 секунды, но останавливалась, пока вкладка скрыта. Человек в Telegram, поэтому после подтверждения вход не завершался.
3. Номер входа жил только в памяти. Если телефон выгружал или перезагружал вкладку, ничего не продолжалось.

## Что стало

### Одно нажатие

Прямо в обработчике нажатия, до первого `await`, страница резервирует место для Telegram.

- Компьютер. `window.open('', '_blank')`, а после ответа сервера вкладке задаётся адрес `https://t.me/<бот>?start=login_…`.
- Телефон (грубый указатель, ширина до 700 px или Android/iOS в user agent) и заблокированное окно. Текущая вкладка уходит на ссылку. t.me открывает приложение через universal links. После возвращения страница продолжает вход (см. ниже).
- Если сервер ответил ошибкой, зарезервированная вкладка закрывается.
- Ссылка «Открыть Telegram» осталась как запасная. Рядом новая ссылка «Открыть приложение Telegram» (`tg://resolve?domain=<бот>&start=<параметр>`) для Telegram Desktop.
- То же сделано для «Подключить Telegram» в окне привязки и «Подтвердить через Telegram» в окне удаления.
- В адрес по-прежнему попадает только одноразовый стартовый токен.

### WebSocket

Сокет только сообщает, что что-то изменилось. Он не создаёт сессию и не передаёт секретов. После `confirmed` страница вызывает прежний `GET /api/v1/auth/telegram/status/{login_id}`, и тот ставит cookie как обычно.

| Адрес | Кто может слушать | Сообщения |
|---|---|---|
| `GET /api/v1/auth/telegram/ws/{login_id}` | браузер, который начал вход (cookie привязки `notes_tg_login`, как у status) | `pending`, затем `confirmed`, `expired` или `used` |
| `GET /api/v1/account/delete-request/telegram/ws/{login_id}` | вошедший аккаунт, которому принадлежит запрос на удаление | те же |
| `GET /api/v1/telegram/links/ws` | вошедший аккаунт | `{"pending": [id…], "linked": N}` при каждом изменении |

Сервер раз в секунду читает строку из базы (каждый раз новая сессия БД), шлёт `pending` один раз, затем итог и закрывает сокет. Сокет закрывается и после окончания входа, и через 6 минут, и когда клиент ушёл. Сессия аккаунта проверяется на каждом шаге, поэтому после выхода сокет закрывается с 4401.

Коды закрытия. Страница не показывает их человеку, при любом закрытии она остаётся на опросе.

| Код | Причина |
|---|---|
| 4401 | нет сессии |
| 4403 | заголовок `Origin` не равен `NOTES_PUBLIC_ORIGIN` (или его нет) |
| 4404 | вход не найден, чужой или привязка не совпала. Подробностей не сообщается |
| 4429 | слишком много рукопожатий или открытых сокетов |
| 1000 | нормальный конец |

Закрытие до `accept` браузер видит как ошибку рукопожатия (HTTP 403, код 1006). Это нормально.

Проверка `Origin` обязательна, потому что cookie уходят и при межсайтовом рукопожатии.

Лимиты:

- не больше 20 рукопожатий в минуту с адреса (общий `throttle`);
- не больше 3 открытых сокетов с адреса и 3 на аккаунт (для окна удаления и привязки);
- числа можно менять настройками `ws_per_ip`, `ws_per_account`, `ws_handshakes_per_minute`, `ws_poll_seconds`, `ws_max_seconds` (по умолчанию 3, 3, 20, 1.0, 360.0). Из переменных окружения они не читаются.

Счётчики открытых сокетов лежат в памяти процесса. Если API работает в нескольких процессах, лимит действует на каждый процесс отдельно. Счётчик рукопожатий общий, он в базе.

Адрес клиента за Caddy. Сервер запущен с `--no-proxy-headers`, поэтому адрес соединения всегда адрес прокси. Для сокетов настоящий адрес берётся из последнего значения `X-Forwarded-For`, и только если соединение пришло с частного адреса (прокси этого же сервера). Caddy сам подставляет адрес клиента. Без этого три сокета на «адрес» значили бы три сокета на весь сайт. Остальные ограничения проекта (например `throttle` в других маршрутах) этой правки не получили.

WebSocket-маршруты не попадают в OpenAPI, контракт `docs/integration-v1.*` не менялся.

### Страница не теряет вход

- Страница открывает сокет при старте входа. На `confirmed` она вызывает status и входит.
- Опрос остался как запасной путь. Пока сокет открыт, он идёт раз в 10 секунд. Без сокета, при его ошибке или закрытии, раз в 2 секунды. В скрытой вкладке опрос больше не останавливается, а идёт раз в 10 секунд.
- Сразу проверка при возвращении: `visibilitychange` (вкладка стала видимой), `pageshow` (в том числе из bfcache), `focus`, `online`. Если сокет умер, он открывается заново.
- Два сигнала подряд делают один запрос: пока идёт проверка, второй сигнал ждёт её конца.
- В `sessionStorage` под ключом `beresta-tg-flow` лежат `{id, expires, purpose}`. Это номер входа и срок, секретов нет. Исходная ссылка и стартовый токен не сохраняются. Запись нужна строго для входа, поэтому не зависит от выбора по cookie. Чтение и запись обёрнуты в try/catch, без хранилища всё работает, кроме возобновления.
- При загрузке страница возобновляет незаконченный вход («Завершаем вход…»), открывает сокет и опрос. Запись стирается после входа, окончания срока, отмены и ошибки. Если вход уже завершён в другой вкладке и страница открыта в приложении, ошибка не показывается.
- Окно удаления возобновляется так же, как только появляется рабочее пространство. Окно привязки (`beresta-tg-link`, только номер запроса и срок) открывается снова и само подтверждает запрос, когда бот его прислал.

### CSP

В заголовок добавлено `connect-src 'self' ws(s)://<хост NOTES_PUBLIC_ORIGIN>`. Часть версий Safari не считает `'self'` достаточным для wss. Для `http://` в разработке используется `ws://`.

## Выкладка

1. В `requirements.txt` добавлен `websockets==17.2`. Образ нужно собрать заново обычным `Dockerfile`. `Dockerfile.runtime-reuse` не подойдёт, в нём нет этой библиотеки. Без неё uvicorn не примет рукопожатие и ответит 404, а страница останется на опросе.
2. Caddy менять не нужно. `reverse_proxy` проксирует Upgrade для WebSocket по умолчанию. `encode` и `header` сокету не мешают.
3. Миграций нет. Новых переменных окружения нет.
4. После выкладки в devtools браузера (вкладка Network, фильтр WS) нажать «Войти через Telegram». Должно быть соединение `wss://<домен>/api/v1/auth/telegram/ws/…` со статусом 101 и кадр `{"status":"pending"}`. Если вместо этого 403 или 404, смотреть Origin и версию образа.

## Как проверено

- `tests/test_telegram_live.py`: вход по cookie привязки, чужая cookie, `pending`, затем `confirmed` после внутреннего login-confirm и вход через обычный status, `expired`, повторное использование, предел жизни, Origin, лимит сокетов на адрес и аккаунт, лимит рукопожатий, адрес из прокси, сокет удаления, сокет привязки только для своего аккаунта, конец сессии, CSP.
- `tests/web_auth.cjs`: синхронный `window.open` и адрес после ответа, заблокированное окно, телефон, закрытие вкладки при ошибке, push через поддельный WebSocket, падение сокета, возвращение (focus, pageshow, online, visibilitychange), возобновление после перезагрузки, закрытое хранилище, окно удаления.
- Настоящий Chromium против локального сервера (mock-провайдер, SQLite, тестовый внутренний токен, t.me заменён заглушкой). Компьютер: вкладка открыта, подтверждение через внутренний API, вход за 0,3 с без перезагрузки. Телефон: переход в текущей вкладке, возврат назад, продолжение входа.

Не проверено: живой Telegram и приложение на телефоне, работа за настоящим Caddy и по TLS, поведение bfcache на iOS, запуск `web_auth.cjs` (нужен jsdom).
